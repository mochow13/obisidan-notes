> Build the technical judgment expected of a **Staff+ backend / AI engineer**: architecture trade-offs, distributed-systems reasoning, scalability, reliability, performance, platform design, evolutionary architecture, microservice boundaries, event-driven systems, and production AI.

> This is a curated, deduplicated, high-signal list from **GOTO-branded conferences** in **2024–2026**. It intentionally excludes YOW!, Code BEAM, Lambda Days, book-club episodes, and most GOTO Unscripted material even when those recordings are hosted on Gotopia.

>

## How to use this note

For each talk, capture:

- **Problem / constraints**
- **Architecture and key design decisions**
- **Trade-offs and rejected alternatives**
- **Failure modes / operational lessons**
- **Scale numbers / SLOs / performance characteristics**
- **Evolution path:** why the architecture became what it is
- **Organizational implications:** ownership, team boundaries, platform/API contracts
- **What I would apply differently in my own systems**
- **Staff+ lesson:** how the speaker frames ambiguity, risk, long-term evolution, and cross-team impact

# 🧭 Suggested Staff+ Learning Path

## Phase 1 — Architecture beyond diagrams

1. [ ] [Bottom-up Architecture – Bridging the Architecture Code Gap](https://gotopia.tech/sessions/3131/bottom-up-architecture-%E2%80%93-bridging-the-architecture-code-gap)
2. [ ] [The C4 Model – Misconceptions, Misuses & Mistakes](https://gotopia.tech/sessions/3111/the-c4-model-%E2%80%93-misconceptions-misuses-and-mistakes)
3. [ ] [Software Design, Architecture & Giving Clarity at Scale](https://gotopia.tech/sessions/3932/software-design-architecture-and-giving-clarity-at-scale)
4. [ ] [Master Software Architecture: From Simplicity to Complexity](https://gotopia.tech/sessions/3660/master-software-architecture-from-simplicity-to-complexity)
5. [ ] [Residues: Time, Change and Uncertainty in Software Architecture](https://gotopia.tech/sessions/3595/residues-time-change-and-uncertainty-in-software-architecture)

### What to learn

- Architecture is a **decision system**, not a diagram.
- Keep optionality while uncertainty is high.
- Connect code boundaries to domain boundaries.
- Communicate architectural context at multiple levels.
- Design for evolution rather than attempting to predict the final shape.

## Phase 2 — Distributed systems & asynchronous architecture

1. [ ] [Swimming Through Molasses: How Scale Makes Distributed Systems Slower](https://gotopia.tech/sessions/3438/swimming-through-molasses-how-scale-makes-distributed-systems-slower)
2. [ ] [How Event Driven Architectures Go Wrong & How to Fix Them](https://gotopia.tech/sessions/3264/how-event-driven-architectures-go-wrong-and-how-to-fix-them)
3. [ ] [Operating Event-Driven Architectures with Quality in Mind](https://gotopia.tech/sessions/3260/operating-event-driven-architectures-with-quality-in-mind)
4. [ ] [Scaling EDA Workloads with Kubernetes, KEDA & Karpenter](https://gotopia.tech/sessions/3414/scaling-eda-workloads-with-kubernetes-keda-and-karpenter)

### What to learn

- Coordination costs dominate at scale.
- Asynchrony changes failure handling and observability.
- Backpressure and autoscaling are part of architecture.
- Event contracts are long-lived APIs.
- Reliability needs to be designed into processing semantics.

### What to learn

- Microservices are primarily about **independent change and ownership**, not small deployment units.
- Distributed monoliths are often worse than well-designed monoliths.
- Domain understanding should precede hard distributed boundaries.
- Platforms should expose useful abstractions without hiding consequential constraints.
